Harness03

Không dùng tools[] native — dùng một JSON quyết định

  • Mỗi lượt LLM trả về đúng một object: {type:"reply"} hoặc {type:"tool"}. Không có tool_calls[], không multi-call trong một lượt.
  • Ép cấu trúc bằng response_format: json_schema. Trên LM Studio / llama.cpp đây là grammar-constrained decoding: model bị chặn ở từng token, không thể sinh JSON sai cú pháp.
  • Cú pháp tool_calls native phức tạp hơn nên model nhỏ dễ lệch — và không có chỗ tự nhiên để nhét reasoning hay để một reply mang kèm đề xuất tool.
  • Thứ tự field trong schema là đòn bẩy prompt cho model nhỏ (slide 06). Với tool_calls, thứ tự đó do SDK serialize — không control được.
  • strict: false có chủ đích: đổi lấy tương thích rộng với LM Studio, Ollama, Gemini-compat.

Harness làm 4 việc — model chỉ làm 1

01 · Mô tả thế giới

Có tool gì, ngưỡng nào

Tool catalog + ngưỡng số của cây dâu được render thành text và bơm vào system prompt mỗi lượt.

02 · Ép định dạng

JSON schema + Zod

Grammar-constrained lúc sinh, Zod validate lúc nhận, một lần nudge nếu parse fail, rồi fallback tĩnh.

03 · Điều phối

Vòng lặp ≤ 3 bước

Tool đọc chạy xong thì nạp kết quả lại vào messages để model quyết định tiếp — không tự do vô hạn.

04 · Chặn hành động

Xác nhận trước khi làm

Đọc thì tự chạy; điều khiển thì tạo pendingAction và chờ người dùng nói "có". Tool lạ mặc định là điều khiển.

Việc duy nhất của model: chọn một trong hai nhánh và điền tham số. Nó không được phép chạy gì, không được phép nhớ gì, không được phép quyết định thời điểm thực thi.

Harness · 0105

Dạy model biết có tool gì: catalog dịch thành text

  • Mỗi tool = một dòng: tên, tham số lấy từ inputSchema, nhãn an toàn, mô tả tiếng Việt. Không đưa JSON schema thô của MCP cho model đọc.
  • Nhãn ĐỌC ĐIỀU KHIỂN nhúng thẳng vào catalog — model thấy ngay tool nào phải xin phép, không phải tự suy luận.
  • Thứ tự block cố định: vai trò → phạm vi (chỉ cây dâu) → khoảng tối ưu từ profile → catalog → 12 quy tắc → few-shot → quy tắc văn xuôi đặt cuối cùng.
  • Prompt được build lại mỗi lượt chat, không cache: đổi profile hay rebuild RAG là có hiệu lực ngay lượt sau.
  • MCP chết lúc khởi động → fallback catalog tĩnh 12 tool. Điều khiển sẽ báo lỗi, nhưng model vẫn "biết đường".

Harness · 0206

Hợp đồng duy nhất giữa harness và model

  • Hai schema tách biệt: JSON Schema định hướng lúc sinh, Zod validate lúc nhận. Không dùng chung một cái cho hai việc.
  • reasoning liệt kê đầu tiên: backend sinh theo thứ tự schema, nên model buộc phải viết vài token suy nghĩ trước khi chốt type — chain-of-thought giá rẻ, và không bao giờ lộ ra người dùng.
  • required: ['type'] — schema lỏng có chủ đích, chấp nhận model bỏ field khác thay vì fail cả request.
  • Parse fail → nudge đúng một lần ("chỉ trả về đúng một JSON hợp lệ") → fail nữa thì trả câu fallback tĩnh. Không có vòng lặp vô hạn.
  • Hai nhiệt độ khác nhau: 0.1 cho quyết định, 0.3 cho câu văn.

Harness · 0408

Bốn lớp lưới an toàn quanh một model không đáng tin

  • Phân loại fail-safe: 6 tool đọc / 6 tool điều khiển ghi cứng; tool lạ chỉ được coi là đọc nếu khớp prefix get_ list_ read_ fetch_ query_ — còn lại mặc định là điều khiển. Thà hỏi thừa hơn chạy nhầm.
  • pendingAction có TTL 30 phút: gõ "có" sau ba tiếng thì lệnh cũ đã hết hiệu lực, không thực thi.
  • Xác nhận free-text tiếng Việt: regex neo đầu chuỗi với boundary lookahead — bắt "có / ừ / ok / đồng ý / làm đi" và "không / hủy / đừng / thôi". Không khớp gì → xoá pending, coi là yêu cầu mới.
  • sanitizeArgs: chỉ giữ key có trong inputSchema của tool — chặn tham số model bịa ra trước khi tới MCP.
  • isTruncatedReply: câu trả lời rỗng hoặc kết thúc bằng dấu : thì regenerate, không đẩy mảnh vụn cho người dùng.
src/mcp/policy.ts:39
export function classifyTool(name) {
  if (READ_ONLY.has(name))  return 'read'
  if (CONTROL.has(name))    return 'control'
  if (READ_PREFIXES.some((p) => name.startsWith(p)))
    return 'read'
  return 'control'   // fail-safe
}
An toàn (classifyTool) tách khỏi trải nghiệm xác nhận: hai tool đọc cảm biến vẫn là read, nhưng khi model chỉ đề xuất đo thì harness hỏi trước; còn khi người dùng hỏi thẳng "độ ẩm bao nhiêu?" thì chạy ngay — chính câu hỏi đó là sự đồng ý.
Speaker notes Test có tên thẳng: "fails safe: unknown tool defaults to control", dùng reboot_everything làm ví dụ. Đây là slide nên chậm lại nếu khán giả có lead/PM: nó là lý do dự án dám nối LLM vào thiết bị thật.

Chỉ field message được lên wire

  • Decision JSON được scan tăng dần từng ký tự bằng parser tự viết: track độ sâu object/array, trạng thái trong-chuỗi, escape, \uXXXX.

  • Frame reset cho phép "xoá cái vừa hiện" khi phải sinh lại — tự phục hồi giữa stream.

Dữ liệu · lớp 414

Đo, chứ không đoán: 45 case tiếng Việt

  • Exact accuracy — đúng cả type và đúng tên tool cụ thể.
  • Safety-class accuracy — tách riêng vì chọn sai tool nhưng cùng lớp đọc khác hẳn về mức nguy hiểm với việc chọn nhầm sang điều khiển.
  • Grounding — heuristic xác định, không dùng LLM-judge: có dẫn nguồn không, số bắt buộc có xuất hiện không, số sai có bị cấm không (ví dụ "30%").
  • Eval chạy có RAG context thật, gọi LLM thật — giống production, nên cần LM Studio sống và không chạy được trong CI.
  • npm test (263 test) chỉ kiểm cấu trúc dataset: đủ case, phủ hết 12 tool, nhãn an toàn đúng.

Demo15

Ba bước, chứng minh cả hai điều quan trọng

1
Trả lời từ RAG, token chảy theo thời gian thực
curl -N -X POST localhost:8787/chat/stream \
  -H 'content-type: application/json' \
  -d '{"userId":"demo","sessionId":"d1",
       "message":"Cây dâu bị vàng lá, nên làm gì?"}'
Kỳ vọng: nhiều frame event: token chảy dần, rồi một event: done.
2
Yêu cầu điều khiển — server hỏi lại, tool chưa chạy
curl -s -X POST localhost:8787/v1/chat/completions \
  -H 'content-type: application/json' \
  -d '{"model":"plant-assistant","session_id":"d2",
       "messages":[{"role":"user",
       "content":"Tưới nước cho esp32-01 10 giây"}]}'
Kỳ vọng: content chứa (Có/Không), tool_calls[0].function.name = set_pump — và log MCP im lặng.
3
Xác nhận bằng đúng hai chữ — không cần echo lại gì
curl -s -X POST localhost:8787/v1/chat/completions \
  -H 'content-type: application/json' \
  -d '{"model":"plant-assistant","session_id":"d2","messages":[{"role":"user","content":"có"}]}'
Kỳ vọng: "Đã thực hiện" — đây là lúc set_pump thật sự chạy qua MCP. Đổi thành "không" → "Đã hủy", không lệnh nào được gửi.
Bước 3 chứng minh cùng lúc hai thứ: an toàn hành động (control không tự chạy) và session server-side (client chỉ gửi "có" + session_id, không phải echo lại tool_calls — thứ mà client rất dễ làm sai).
Speaker notes Nếu MCP chưa sẵn sàng lúc demo, bước 3 vẫn trả 200 nhưng nội dung sẽ báo lỗi route (404 / -32601). Đó cũng là behavior đáng demo: hệ thống không giả vờ thành công. Nói trước câu đó thì sự cố thành điểm cộng.

Điều đáng mang về

  • Model nhỏ không cần thông minh hơn — cần một hợp đồng chặt hơn. Một JSON, hai nhánh, năm field.
  • Ép cấu trúc ở tầng decoding đáng tin hơn dặn dò trong prompt. Grammar-constrained thắng "hãy trả về JSON nhé".
  • Quyết định thì để model, thực thi thì để code. An toàn nằm đúng ở ranh giới đó, không nằm trong prompt.
  • Mọi mẹo cho model nhỏ phải có test khoá lại — vì regression ở đây im lặng: không exception, chỉ là câu trả lời tệ dần.
